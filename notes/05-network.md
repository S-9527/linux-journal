## 1. 本机网络实况

```console
$ ip -brief addr show
lo               UNKNOWN   127.0.0.1/8
eth1             UP        192.168.1.8/24  2409:8a34:.../64
br-95388b7a9bc1  UP        172.19.0.1/16
docker0          DOWN      172.17.0.1/16
```

三类网卡，注意区分：

| 网卡 | IP | 作用 |
|---|---|---|
| `lo` | 127.0.0.1 | 回环，只有本机能连 |
| `eth1` | 192.168.1.8 | WSL 虚拟网卡，宿主 Windows 的视角 |
| `br-*` / `docker0` | 172.x | Docker 网桥 |

```console
$ ip route
default via 192.168.1.1 dev eth1 proto kernel metric 50
192.168.1.0/24 dev eth1 proto kernel metric 306
172.19.0/16 dev br-95388b7a9bc1 proto kernel scope link src 172.19.0.1
```

`default via 192.168.1.1` = 默认网关，即"去任何地方都先问它要路"。

### WSL2 的 DNS 特殊之处

```console
$ cat /etc/resolv.conf
# This file was automatically generated by WSL. To stop automatic generation, add the following entry to /etc/wsl.conf:
# [network]
# generateResolvConf = false
nameserver 10.255.255.254
```

**这个文件由 WSL 自动生成，每次重启可能被覆盖。** 想固定 DNS 必须先在 `/etc/wsl.conf` 里关掉自动生成。

## 2. `127.0.0.1` vs `0.0.0.0`（新手第一大坑）

这是"服务起来了但别人访问不了"的头号原因。

### 实测：同一个程序，两种绑定

**情况 A：监听 `127.0.0.1`**

```console
$ ss -tln | grep 18085
LISTEN 0 5   127.0.0.1:18085   0.0.0.0:*

$ curl http://127.0.0.1:18085/    → HTTP 200
$ curl http://192.168.1.8:18085/  → HTTP 000 (拒绝)
```

**情况 B：监听 `0.0.0.0`**

```console
$ ss -tln | grep 18085
LISTEN 0 5   0.0.0.0:18085   0.0.0.0:*

$ curl http://127.0.0.1:18085/    → HTTP 200
$ curl http://192.168.1.8:18085/  → HTTP 200
```

| 地址 | 含义 |
|---|---|
| `127.0.0.1` | **只有本机**的回环接口 |
| `0.0.0.0` | **所有**网卡（通配地址） |
| `192.168.1.8` | 绑定到指定的那张网卡 |

**开发服务器的默认值往往是 `127.0.0.1`（安全默认），生产环境要改成 `0.0.0.0` 才能被外部访问。**

### 排查"访问不了"的顺序

```console
$ ss -tlnp | grep 8080
LISTEN 0 4096  127.0.0.1:8080  0.0.0.0:*  users:(("node",pid=1234,fd=20))
                    ↑ 这里就是答案
```

1. 服务在跑吗 → `systemctl status xxx` / `ps aux`
2. 监听了吗 → `ss -tlnp`（看绑定的是 127.0.0.1 还是 0.0.0.0）
3. 端口对吗 → 别把容器内端口当成了宿主机端口
4. 防火墙放行了吗 → `sudo ufw status` / `iptables -L`
5. 云服务器还有安全组 → 这是另一层，在控制台配

## 3. 排查时的一个陷阱：代理环境变量

实测中遇到一个很有代表性的问题：

```console
$ curl -v http://192.168.1.8:18085/
*   Trying 127.0.0.1:10808...        ← 请求被送去代理了！

$ env | grep -i proxy
HTTP_PROXY=http://127.0.0.1:10808
NO_PROXY=192.168.*,172.31.*,...,127.*,localhost
```

**明明 `NO_PROXY` 里写了 `192.168.*`，但 curl 还是走了代理。** 原因：`NO_PROXY` 支持 CIDR 和通配，但**主机名和 IP 的匹配规则各家实现不同**，且 `192.168.*` 这种写法在部分版本里不生效。

解法：

```bash
curl --noproxy '*' http://192.168.1.8:8080/     # 显式绕过
```

**这也是"本地能访问、局域网访问不了"的一个隐蔽原因** —— 你的客户端在代理，而不是服务端的问题。

## 4. HTTP 请求全过程

```console
$ curl -sv http://127.0.0.1:18090/test
*   Trying 127.0.0.1:18090...
* Established connection to 127.0.0.1 (127.0.0.1 port 18090) from 127.0.0.1 port 44934
* using HTTP/1.x
> GET /test HTTP/1.1          ← 以下是【请求】
> Host: 127.0.0.1:18090
> User-Agent: curl/8.18.0
> Accept: */*
>
* Request completely sent off
< HTTP/1.1 200 OK             ← 以下是【响应】
< Server: BaseHTTP/0.6 Python/3.14.4
< Date: Mon, 28 Sep 2026 05:00:07 GMT
< Content-Type: text/plain
< Content-Length: 5
<
hello
```

**顺序：连接 → 请求行 → 请求头 → 空行 → 响应状态行 → 响应头 → 空行 → 响应体。**

`>` 是发出的，`<` 是收到的。排查线上问题时先看 `<` 那一半。

常用变体：

```bash
curl -I url          # 只要响应头（-I = HEAD 请求）
curl -s url          # 静默，不要进度条
curl -o file url     # 输出到文件
curl -X POST -d '{}' url
curl --noproxy '*' url   # 绕过代理
curl -w '%{http_code} %{time_total}s\n' url   # 自定义输出格式
```

## 5. 端口扫描

完整脚本见 [`scripts/05-port-check.sh`](../scripts/05-port-check.sh)。实测输出：

```console
$ ./scripts/05-port-check.sh 127.0.0.1 1
▶ 扫描 127.0.0.1 (超时 1s)

  端口   服务       状态     耗时
  ----   ----     ----     ----
  22     SSH        关闭     12ms
  80     HTTP       关闭     10ms
  443    HTTPS      关闭     9ms
  3000   dev        关闭     11ms
  5432   PostgreSQL  开放     9ms      ← 本机确实跑着 PG
  3306   MySQL      关闭     11ms
  6379   Redis      关闭     11ms
  8080   alt-HTTP   关闭     8ms
  27017  MongoDB    关闭     8ms

汇总  开放 1 / 关闭 8 (共 9)
```

测不存在的地址，验证超时确实生效：

```console
$ time ./scripts/05-port-check.sh 10.255.255.254 1
汇总  开放 0 / 关闭 9 (共 9)
0.145 total            ← 9 个端口 1 秒超时，0.145 秒跑完
```

**超时设置是必须的。** Linux TCP 会对 SYN 重传多次（`tcp_syn_retries=6`，约 127 秒）。不设 `-w` 的话扫一个不存在的地址，一个端口就能把脚本卡住两分钟。

```bash
nc -z -w "$TIMEOUT" -n "$HOST" "$port"
#  -z  成功后发零字节立即断开（Zero-I/O 模式）
#  -w  超时
#  -n  跳过 DNS/协议预检，纯 TCP 连接
```

## 6. SSH

### 密钥对

```console
$ ssh-keygen -t ed25519 -N "" -C "linux-journal-lab" -f ~/.ssh/lab_key
$ ls -l ~/.ssh/lab_key*
-rw-------  1 anguish anguish 411 ~/.ssh/lab_key        ← 私钥必须 600
-rw-r--r--  1 anguish anguish  99 ~/.ssh/lab_key.pub    ← 公钥 644
```

**私钥权限必须是 `600`，否则 ssh 拒绝使用**（防的是同机其他用户偷读）。

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIDPD0nZKsafEkQCopiAOul6YAFCh+ZdOpK0FYlDzLHA4 linux-journal-lab
^^^^^^^^^^^^^^ 算法    ^^^^^^^^ 密钥本身（可公开）              ^^^^^^^^^^^^^^^^^^ 注释
```

**公钥可以随便给（贴到 GitHub、服务器上），私钥永远不能离开本机。**

登录验证机制：服务器把公钥写进 `~/.ssh/authorized_keys`，你用私钥签名，服务器验证签名。**密码从不经过网络传输**（至少不会以明文形式）。

### `~/.ssh/config` —— 强烈建议配

```
Host myserver
    HostName 1.2.3.4
    User deploy
    Port 22
    IdentityFile ~/.ssh/ed25519
    IdentitiesOnly yes          # 不用 agent 里的其他密钥，避免"too many attempts"
    ServerAliveInterval 60      # 每 60s 发心跳，防止 NAT 断连
    ServerAliveCountMax 3

Host bastion
    HostName jump.example.com
    User admin
    ForwardAgent yes            # 允许通过跳板机继续认证

# 二级跳板
Host target
    HostName 10.0.0.5
    User deploy
    ProxyJump bastion           # 等价于 ssh -J bastion target
```

配完之后 `ssh myserver` 一条命令搞定，跟本地目录一样顺手。

⚠️ **`~/.ssh/config` 权限必须是 `600`。**

### 端口转发

```bash
# 本地转发: 本机 8080 → 远程的 127.0.0.1:80
ssh -L 8080:127.0.0.1:80 myserver

# 远程转发: 远程 8080 → 本机 3000
ssh -R 8080:localhost:3000 myserver

# SOCKS 代理（浏览器走它上网）
ssh -D 1080 myserver

# 常用组合: 本地 5432 连远程内网数据库
ssh -L 5432:10.0.0.5:5432 myserver
psql -h 127.0.0.1 -p 5432
```

### 隧道实测

本机没有 sshd，用 Python 实现了等价的双向转发数据流：

```console
内部服务:  127.0.0.1:18092  (只有本机能连)
隧道入口:  127.0.0.1:28081  (本机通过它间接访问)
直连 18092 → INTERNAL-ONLY-SERVICE
经 28081 → INTERNAL-ONLY-SERVICE
```

**`-L` 隧道干的就是这件事：把"远程只能远程访问的端口"映射到本地，你用浏览器直接开。** 这是连内网机器做前端调试的核心技巧 —— 后端跑在远程 `127.0.0.1:3000`，本地 `ssh -L 3000:127.0.0.1:3000 dev@server`，然后浏览器开 `localhost:3000`，跟远程跑一样。

### 文件传输

```bash
scp file.txt myserver:/tmp/
scp -r dir/ myserver:/tmp/
rsync -avz --delete src/ myserver:/dst/

# 只传比目标新的（增量）
rsync -avz --progress src/ myserver:/dst/
rsync -avz --exclude 'node_modules' --exclude '.git' src/ myserver:/dst/
```

⚠️ **`rsync --delete` 会删掉目标目录里有、源目录里没有的文件。** 手滑打错路径就是一场灾难。**养成习惯：先跑 `--dry-run` 看一遍要动什么。**

```bash
rsync -avz --delete --dry-run src/ myserver:/dst/
```

### 常用参数

| 参数 | 作用 |
|---|---|
| `-v` | 详细输出 |
| `-N` | 端口转发不执行远程命令（只做隧道） |
| `-T` | 不分配伪终端（脚本里用） |
| `-o StrictHostKeyChecking=no` | 首次连接不提示（**CI 里常用，有 MITM 风险**） |
| `-J` | 跳板机 |
| `-A` | 转发 agent |

## 7. systemd

本机实测：

```console
$ systemctl --version
systemd 259 (259.5-0ubuntu3.4)

$ systemctl list-units --type=service --state=running
  UNIT                        LOAD   ACTIVE SUB     DESCRIPTION
  chrony.service              loaded active running chrony, an NTP client/server
  containerd.service          loaded active running containerd container runtime
  docker.service              loaded active running Docker Application Engine
```

### 两个必须分清的概念

| 命令 | 作用 |
|---|---|
| `systemctl start xxx` | **现在**启动 |
| `systemctl enable xxx` | **开机**自动启动 |
| `systemctl enable --now xxx` | 两个都做 |
| `systemctl disable xxx` | 取消开机自启（不影响当前运行） |
| `systemctl status xxx` | 看状态 |

**只 start 不 enable → 服务器一重启服务就没了。** 这是新手最常见的"服务莫名其妙消失"原因。

反过来，只 enable 不 start → 永远不会被启动（enable 只是建了个符号链接）。

### 写一个 service

完整示例见 [`labs/05-network/myapp.service`](../labs/05-network/myapp.service)。关键字段：

```ini
[Unit]
Description=My Node.js Application
After=network.target

[Service]
Type=simple
User=myapp                    # 绝不用 root 跑应用
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/node /opt/myapp/index.js   # 绝对路径
Environment=NODE_ENV=production
EnvironmentFile=-/opt/myapp/.env              # 从文件读敏感配置
Restart=always
RestartSec=5
MemoryMax=512M

[Install]
WantedBy=multi-user.target
```

**三个最容易踩的点：**

**① `ExecStart` 必须是绝对路径。** systemd 的 `PATH` 很干净（不加载 `.bashrc`），`node` 这类 nvm 装的命令找不到。

**② 不读 `.bashrc`。** 你的 `export XXX` 在 service 里统统不存在。要设就写 `Environment=`。

**③ 改完必须 `daemon-reload`。**

```bash
sudo systemctl daemon-reload    # 忘了这步 → systemd 还在用旧配置，你会以为改动无效
sudo systemctl enable --now myapp
```

### 日志

```bash
journalctl -u myapp -f              # 实时跟踪
journalctl -u myapp --since "1 hour ago"
journalctl -u myapp -n 100          # 最近 100 行
```

## 思考题答案

### 1. `0.0.0.0` vs `127.0.0.1`

- `127.0.0.1` = 绑定到**回环接口**，只接受本机来源的连接
- `0.0.0.0` = 绑定到**所有**接口（通配），接受任何来源

**"本地能开浏览器、外面访问不了"的原因：**

服务默认只监听 `127.0.0.1`（安全默认）。你在本机用 `localhost` 访问走的是回环，成功；别人从外部访问时目标是你的 `192.168.1.8`，而你的进程根本没在那个地址上监听，内核直接拒绝。

**解法：** 改成 `0.0.0.0`（Node: `app.listen(3000, '0.0.0.0')`；Python: `HTTPServer(('0.0.0.0', 18080), H)`；Nginx: `listen 0.0.0.0:80;`）。

⚠️ **安全提醒：** 改之前先确认有防火墙保护。`0.0.0.0` 意味着**任何能路由到这台机器的客户端**都能连上。

### 2. `-L` 和 `-R` 的使用场景

| | 方向 | 场景 |
|---|---|---|
| `-L` 本地转发 | 本机端口 → 远程服务 | 访问远程内网服务（最常用）；远程 DB 映射到本地 |
| `-R` 远程转发 | 远程端口 → 本机服务 | 把本地开发服务暴露给远程（回调、Webhook 测试）；远程机器访问不到外网时反向代理 |
| `-D` SOCKS | 本机 SOCKS 代理 | 整个浏览器流量走远程 |

**记忆法：箭头起点是你敲命令的那台机器。**

`-L 8080:127.0.0.1:80` 读作"我的 8080，请你去连那台机器的 127.0.0.1:80"。

### 3. `enable` 和 `start` 的区别

- `start` = 立即启动
- `enable` = 创建符号链接到 `multi-user.target`，让 systemd 在**下次开机**时启动

**只 start 不 enable：** 服务现在能跑，但服务器一重启就消失。这是"服务莫名其妙没了"的头号原因。

**只 enable 不 start：** 符号链接建好了，但当前没启动。`systemctl status` 会显示 `enabled` 但 `inactive`。

**正确做法：`systemctl enable --now xxx`。**

### 4. 为什么改完 service 必须 `daemon-reload`

**systemd 会缓存 unit 文件的解析结果。** 进程里的副本不会因为文件变了就自动更新。

- 不 reload → systemd 用的还是旧的解析结果 → 你改了没效果 → 反复检查文件以为改错了
- 某些字段（`ExecStart`）改了**必须 reload**，而 `Environment` 之类某些实现会热加载

**规则：改任何 unit 文件后，一律先 `daemon-reload` 再 `restart`。**

```bash
sudo systemctl daemon-reload
sudo systemctl restart myapp
```

### 5. `Restart=always` 能保证服务绝不挂吗

**不能。** 它管不了这些：

| 情况 | 为什么管不了 |
|---|---|
| **启动就失败** | systemd 达到 `StartLimitBurst`(默认 5 次/10秒) 后放弃，标记 failed，不再重试 |
| **配置错误** | 错的配置重启一万次还是错的，只是刷满日志 |
| **依赖没起来** | 数据库挂了，应用重启也连不上；`Requires=` 只能保证顺序不能保证健康 |
| **机器资源耗尽** | 磁盘满、内存 OOM（OOM 杀的是应用本身，`Restart` 来不及执行） |
| **健康检查失败但进程还在** | `Restart` 只看进程退出，进程活着但服务不可用时不会重启 |
| **systemd 本身挂了** | PID 1 都没了，下面的都无从谈起 |

**补上健康检查：**

```ini
[Service]
Restart=always
RestartSec=5
StartLimitBurst=5
StartLimitIntervalSec=10

# systemd 会周期性跑这个命令，失败就重启服务
# 注意: exit 0 = 健康, 非 0 = 不健康
```

或者用 `Type=notify` 让应用自己报告就绪状态（更准确，但需要应用支持 sd_notify）。

### 6. `rsync --delete` 出了事故是什么后果

**会删掉目标目录里源目录没有的文件，无确认，无回收站。**

典型事故：

```bash
# 源目录拼错，指向了空目录
rsync -avz --delete ~/projec/ server:/opt/app/     # 少个 t
# → 服务器上 /opt/app/ 全部文件被删空
```

```bash
# 反向：把备份同步回去，源是老的
rsync -avz --delete old-backup/ server:/opt/app/
# → 用旧备份覆盖了新代码
```

**防护措施：**

```bash
# 1. 永远先 dry-run
rsync -avz --delete --dry-run src/ server:/dst/

# 2. 加 --backup，删除的挪到 ./~ 目录而不是真删
rsync -avz --delete --backup --backup-dir=/tmp/rsync-backup src/ server:/dst/

# 3. 源目录末尾的 / 极其重要
rsync -avz --delete src/  server:/dst/    # dst 内容 = src 内容（正确）
rsync -avz --delete src   server:/dst/    # dst/src 内容 = src（多套一层）
```
